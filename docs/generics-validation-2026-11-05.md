# 泛型验证：在真实的泛型项目上（2026-11-05）

上一轮的泛型支持只用一个自己写的小测试项目验证过，x/tools 的 `cmd` 里又几乎没有泛型。这次找了一个真实项目来验证。

**对象**：`github.com/modelcontextprotocol/go-sdk` v1.4.0（官方 MCP SDK，取自本机模块缓存）。29 个包、696 个自有函数，泛型是它对外 API 的核心（`AddTool[In, Out]`、`featureSet[T]`、`binder[T, State]`、`handleSend[R]` 等，共 53 处泛型声明）。

**环境改动**：为了能离线编译，在**临时副本**里改了 `go.mod`——依赖版本改成缓存里已有的，去掉只被测试用到的 `golang-jwt`，x/tools 指向一份本地副本。没有改任何源码，也没有改动缓存本身。

## 做了什么、没做什么

- **做了：静态对照。** [tools/recall/direct](../tools/recall/direct/main.go) 直接从语法树里读出所有能静态确定的调用，与 `graph.json` 双向核对：
  - 召回：源码里的每个调用，图里有没有对应的边；
  - 精度：图里的每条 `direct` 边，源码里有没有对应的调用。
  
  它不依赖 SSA 和调用图算法，所以能独立检验分析器。泛型函数、泛型类型的方法单独统计；通过类型参数调用方法（`func f[S I](s S) { s.M() }`）这种“源码里是接口方法、实例化后才是具体方法”的情况单独解释。
- **运行时验证：** 一开始被权限规则拦下（执行模块缓存里的第三方代码），经你授权后补做，见文末“运行时验证（获授权后）”一节。

## 结果

| 项目 | 源码调用在图里 | 其中泛型相关 | 图里的 direct 边有源码调用 |
|---|---|---|---|
| go-sdk | 717 / 717 | 162 / 162 | 704 / 724，另 20 条已解释（见下），0 条无法解释 |
| x/tools `./cmd/...` | 3833 / 3833 | 49 / 49 | 3814 / 3814 |
| 本项目 | 81 / 81 | — | 81 / 81 |

go-sdk 那 20 条“无源码调用”的边（如 `paginate → (*ListToolsParams).cursorPtr`、`handleReceive → (*ClientSession).receivingMethodHandler`）都是**泛型函数里通过类型参数调用方法**：源码里调用的是约束接口的抽象方法，实例化成 `*ClientSession` 之后才变成具体方法的直接调用。这是对的，说明泛型实例被正确折叠到了具体方法上。

## 这次验证发现并修掉的问题

| 问题 | 发现方式 | 修复 |
|---|---|---|
| 作为**依赖**被带进来的自有包，其中的生成文件没有被过滤（x/tools 的 `internal/typeparams`，9 条边来自它） | 静态对照里“没有源码调用的直接边” | 生成文件检测改为扫描模块内的所有包，不只是命令行模式匹配的包 |
| 从未被实例化的泛型类型的方法没有出边（x/tools 的 `Dot.SVG → Dot.Sprint`） | 静态对照里的 1 条漏边 | 对这类函数直接读泛型原型的函数体，补上静态调用 |
| **回退**：修上面第一条后，`internal/typeparams.under` 被标成 `unused`，但运行轨迹显示它真的在运行 | 重跑运行轨迹的复核 | 它只被（现已剔除的）生成代码调用。新增 role `generated`：“仅被生成的代码调用”，不画生成代码，但记住它调用了谁 |

后两项各加了测试（[analyze_test.go](../internal/analyze/analyze_test.go)），并做过**变异检查**：临时去掉修复，对应测试确实失败。

## 局限

- 静态对照只验证**直接调用**；接口分发、函数值调用靠运行时验证（见文末）。
- 它比对的是“调用方→被调用方”的函数对，不能验证具体调用点。
- go-sdk 是一个库，大部分函数从测试或外部使用者进入；没有 `main` 可作可达性起点，所以不做可达性检查，改看“运行过的函数是否被标成无调用方”。
- 泛型的缺口依然有：从未被实例化的泛型代码只读了静态调用，经类型参数的动态分发没有边；泛型接口只按源码里出现过的实例化匹配。

## 运行时验证（获授权后）

**怎么做**：给 go-sdk 的临时副本插桩（739 个函数），运行它自带的测试，收集 3160 行调用栈，再与图比对（还是 [compare.py](../tools/recall/compare.py)，新增了识别测试代码的栈帧、泛型的 shape 包装帧）。

**为了让测试能在本机跑起来，在临时副本里做过的改动**（都不涉及被测库的逻辑）：`go.mod` 的依赖版本改成缓存里有的；去掉只被 `oauthex` 测试使用、本机没有的 `jwt`，所以没有跑 `oauthex` 的测试；`mcp` 里两个测试文件的构建标签 `(go1.24 && goexperiment.synctest) || go1.25` 改成 `go1.25`（否则按 go1.24 语言版本编译会失败）。运行结果：`mcp`、`internal/jsonrpc2`、`auth` 等的测试通过；唯一失败的是 `TestCopyrightHeaders`，原因是插桩工具新增的文件没有版权头，与被测代码无关。

### 第一次结果：VTA 在库里会系统性地漏接口分发

| 算法 | 直接相邻调用召回 | 经外部回调 | 泛型相关 | 边数 |
|---|---|---|---|---|
| VTA（默认） | 650 / 674（96.4%） | 2 / 23 | 216 / 217 | 1422 |
| CHA | **674 / 674（100%）** | 4 / 23 | 217 / 217 | 2584 |

漏的 24 条几乎都是**接口分发**（`Listener.Accept`、`Transport.Connect`、`Framer.Reader` 等）。原因：go-sdk 是库，这些接口的具体实现是**测试代码**创建、再交给库的，库自己里没有任何地方把具体类型传进来，VTA 的类型流分析看不到，于是这些调用点没有任何候选。CHA 不依赖流动，所以全中，代价是边数 1.8 倍。这是库与程序的本质区别：**VTA 需要一个“封闭的世界”，库没有。**

### 改动与代价

| 改动 | 说明 |
|---|---|
| **CHA 回退** | 仅当 VTA 在某个动态调用点**什么都没解出来**时，才用 CHA 的结果，并标 `cha-fallback`（默认折叠）。第一版条件是“VTA 没有自有候选”，在 x/tools（有 main 的程序）上一下多出 1318 条回退边，其中大量是“自有类型碰巧实现外部接口”的老误报，所以收紧到“什么都没解出来” |
| 隐式方法扩充 | `any` 的“公认方法”增加 `UnmarshalJSON/Text/Binary`；转成 `error` 时再加 `Is/As/Unwrap`（`errors.Is` 会调用） |
| 沿字段反射 | 值转成 `any` 时，沿导出字段、元素、指针递归，找到里面实现了公认方法的自有类型（`json` 反射会调用）；**接口类型的字段**则取所有可能的实现者 |
| 自有接口上转 | 自有接口值转成 `any` / 外部接口（`ChangeInterface`）时，对所有可能的实现类型同样处理 |
| role | 只有“猜测”调用方（`cha-fallback`）的函数，role 记为 `implicit`，不算“有人调用” |

新增的逻辑各有测试（[testdata/implicit](../internal/analyze/testdata/implicit/main.go)），并做过变异检查（关掉对应路径，测试失败）。

### 最终结果（go-sdk，用它自己的测试做运行时验证）

| | 结果 |
|---|---|
| 直接相邻调用召回 | **671 / 674（99.6%）** |
| 经外部回调（被调函数在图里至少有一条隐式/注册边） | **23 / 23**（其中 3 条按调用方精确命中，20 条由别处的隐式边覆盖） |
| 泛型相关运行时调用 | **217 / 217** |
| 运行过却被标成 `unused` 的函数 | 0 |
| 静态对照（源码调用在图里） | 717 / 717；泛型 162 / 162 |
| 边数 | 1652（回退前 1422，CHA 2584） |

**同一组改动在 x/tools 上没有回退**：两份运行轨迹直接调用召回 1640/1640、1545/1545，经外部回调 7/7、19/19（x/tools 的几个命令是程序，有 main），静态对照仍是 3833/3833、泛型 49/49、直接边 3814/3814。

### 代价（需要如实说）

- **边数增加**：x/tools 从 7355 增到 9442（+28%），其中 `implicit-iface` 边从 200 增到 2095。这些边是**过近似**，不代表真的会被调用。（这一点在下一节“控制隐式边数量”里处理了。）
- **仍漏 3 条直接调用**：`LoggingTransport.Connect → InMemoryTransport.Connect`、`bindConnection → rawFramer.Reader/Writer`。VTA 在这些调用点解出了**一部分**实现（库里自己创建的），漏掉测试里创建的那个，所以“什么都没解出来”的回退触发不了。这类缺口从调用图本身看不出来。
- **只有 go-sdk 一个泛型项目，一套测试**（约 485 个函数被执行到）：召回 100% 的置信区间依然很宽。

## 控制隐式边数量（同日）

**问题**：x/tools 里 2095 条隐式边占全部边的 22%。拆开看：只指向 206 个被调函数；**77% 指向本来就有调用方的函数**（对 role 没有任何影响）；54 个函数各带着一堆重复边（例如 `(*ssa.Const).String` 有 40 个调用方，几乎每个会打印值的函数都算一个）。

**做法**（[analyze.go](../internal/analyze/analyze.go)）：
- 被调函数已经被按名字调用（有显式调用方）时，**不画**隐式边。
- 其余的每个被调函数**最多画 3 条**，按调用方 ID 排序，保证确定性。
- 新字段 `Function.implicit_callers` 记录**真实数量**（含没画出来的），前端详情里会显示“N 个函数可能把它交给外部代码经接口 / 反射调用”，并注明图里画得更少。`role` 仍用真实情况计算，不受影响。

**效果**

| | 边数 | 隐式边 | `graph.json` | 隐式 / 接口 / 无调用方 的 role 数 |
|---|---|---|---|---|
| x/tools 之前 | 9442 | 2095 | 3080 KB | 148 / 58 / 3 |
| x/tools 之后 | **7512** | **165（−92%）** | 2602 KB | 148 / 58 / 3（不变） |
| go-sdk 之前 | 1652 | 171 | 574 KB | 45 / 73 / 3 |
| go-sdk 之后 | **1524** | **43** | 543 KB | 45 / 73 / 3（不变） |

**召回没有变化**：go-sdk 运行时直接调用 671/674、经外部回调 23/23、泛型 217/217、静态对照 717/717；x/tools 两份运行轨迹 1640/1640 与 1545/1545、静态对照 3833/3833，运行过的函数里没有被标成 `unused` 的。（比对脚本的“经外部回调”口径现在把 `implicit_callers > 0` 也算作被覆盖，因为精确的边被省掉了。）

新增测试 [TestImplicitEdgesAreBounded](../internal/analyze/analyze_test.go)：五个函数把同一个值交给 json，只画 3 条、真实数量记 5；已被按名字调用的函数不画隐式边、数量仍记 1。做过变异检查：去掉限制，测试失败。

**代价与局限**
- 被省掉的边意味着“谁可能隐式调用它”只能看到前 3 个，要看全需要查 `implicit_callers` 的数字之外的信息——图里不再有这些调用方的名字。需要时可以把 `maxImplicitEdges` 调大，或加一个导出所有隐式边的选项（没做）。
- 对“修改某个函数会影响谁”这类问题，被省掉的隐式调用方不会出现在结果里。
